## CRM contract evidenced by local source

- `POST /api/v1/integrations/website-leads`; `Authorization: Bearer ed_live_…` with 43 key characters after the prefix. The server hashes and checks the key, rejects revoked keys and requires an active associated project. Key creation requires a CRM administrator. The project is selected by the key, not by a WordPress project ID or incoming project name.
- Canonical input accepts `customer_name` (1–150 characters), `mobile` (string, 7–20 characters matching the local phone expression), and literal `consent: true`. Optional: `email`, `message` (up to 3000), `external_id` (1–150), `interest`, `project`, `category`, `plot_size`, `budget`, `timeline`, `visit_date`, `page_url`, `utm_source`, `utm_medium`, `utm_campaign`. Most context fields have a 200-character limit; page URL has 2048. Schema limits are authoritative. `plot_number`, `source` and `location` are not standalone fields in this contract; preserve relevant approved context in supported message fields with bounds. Never infer consent.
- `X-EstateDesk-Format: canonical` selects canonical names instead of a key's saved mapping. Existing mapping rejects ambiguous aliases and supports constrained paths.
- New lead: HTTP 201 with `{success:true,data:{enquiry_id,duplicate:false}}`; a retry with the same `(API key, external_id)` returns HTTP 200 with `duplicate:true` and the same enquiry ID. A database unique key and a key row lock protect this scope. No independent `Idempotency-Key` behavior is implemented. Dedupe across different or replaced keys is not guaranteed.
- Authenticated GET on the same endpoint can filter by `external_id` and lists records associated with the same key; results contain customer data and must be handled accordingly. The local shared public limiter is 30 requests per 15 minutes; deployment topology or additional limits may differ.
- The supplied URL is on the Vercel frontend. The checked-in `frontend/vercel.json` has no `/api/v1` rewrite; the local frontend uses `VITE_API_BASE_URL`. This does not prove current deployed routing or Vercel protection status. Confirm the actual public backend HTTPS origin and deployment protection with the operator. An earlier 401 could have multiple causes and has not been diagnosed by an authenticated test. Never disable protection to bypass it.

## Local bridge risks requiring implementation and tests

Existing repair copies are already modified in the worktree. The 1.1.3 bridge has a database queue, stable source IDs, an atomic claim, a bounded retry count and confirmation of a CRM enquiry ID. However, it lacks required queue fields and reporting, jitter and a durable next-attempt timestamp; delivery can run at shutdown, worker scheduling depends on WP-Cron unless externally invoked, and stale-worker recovery and simultaneous claims need real database concurrency tests. Automatic scheduling, manual retry and attention states need full review. Its endpoint validation is not a specific hostname allowlist. Queue payload retention/deletion, protected credential constants, mapping edge cases and administrative capabilities require further work. The JSON importer permits scalar phone values, which can lose leading zeros before conversion. Local chatbot has an independent legacy HTTP path. Local Nestoria accepts and saves a lead even when enqueue fails, and no durable recovery of that failure is shown. Source-specific IDs may collide across installations sharing a key. Do not package these copies as a completed production solution.

## Plan and gates

1. Obtain the actual active plugin packages (including contact form, snippets and site-specific customizations), sanitized plugin inventory and configuration, plus a staging clone. Inventory every submitted form and verify storage, emails and consent before selecting adapters. Compare installed files to the modified local copies without replacing either.
2. Confirm the deployed CRM backend origin, protection rules and project-scoped key through a secure administrator-managed channel. Use an approved synthetic identity on staging. Establish the deployed contract and baseline 401 cause; no secret is needed in chat.
3. Finish contract, validation, field mapping and preview tests; identify supported treatment for plot and other context. Design stable globally unique submission IDs and a database-backed recovery path when local save succeeds but enqueue fails.
4. Implement additive migrations, centralized queue and source adapters with atomic claims, retry jitter, stable identity, error classification, retention and secure settings. Preserve existing source and email workflows. Configure a real server scheduler.
5. Implement monitoring, filters, protected retries and diagnostics; complete the requested automated tests, including database concurrency and failure recovery. Validate on staging with synthetic data, including source-specific UI and email regressions.
6. Prepare versioned packages, migration and rollback instructions, and a precise acceptance report. Deploy only against verified installed versions; verify one CRM lead and duplicate retry behavior using an authorized test identity. Do not mark acceptance complete without evidence.
