# Final Development Specification — Real Estate CRM & Plot Inventory Management System

Requirements finalized Development specification v1.0

The product scope is now finalized based on your five decisions.

The system will be a web-based Real Estate CRM with mobile-responsive access, connected to your existing website through APIs. It will support multiple projects, interactive plot layouts, real-time inventory, employee and broker access, customer management, and manager-approved bookings.

The uploaded Ratanpur layout (Survey No. 254/1) will be the reference for the interactive plot management module.

## 3. Interactive plot layout — detailed specification

This is the most important custom development component because it must reproduce the functionality of your uploaded layout.

### 3.1 Layout digitization

The uploaded image will initially be used as the background reference.

The development team must:

1. Upload the original high-resolution project layout.
2. Store the original image without alteration.
3. Create a digital coordinate system over the image.
4. Trace each individual plot boundary.
5. Assign a unique plot record to each boundary.
6. Match the boundary with its actual plot number.
7. Enter the corresponding plot area and measurements.
8. Verify all plot positions against the original layout.
9. Save the editable layout.

Important: Do not use OCR or automatic image detection as the sole source of plot boundaries. The image is a reference, and each plot must be verified against the actual survey/layout plan.

### 3.2 Layout editor

The administrator should have an editing interface with:

- Upload background image.
- Add plot boundary.
- Draw polygon.
- Edit polygon points.
- Move plot boundary.
- Resize boundary.
- Assign plot number.
- Assign plot database record.
- Delete an incorrect boundary.
- Undo and redo.
- Zoom and pan.
- Save draft.
- Publish layout.
- Restore previous layout version.

Use SVG polygons for plot boundaries, with an image background.

Each polygon should have a permanent plot ID, so changing the visual position never changes the underlying inventory record.

### 3.3 Example layout data structure

A plot boundary can be stored as normalized coordinates from 0 to 1.

json

```json
{
  "plot_id": "uuid",
  "plot_number": "01",
  "layout_id": "uuid",
  "geometry": {
    "type": "Polygon",
    "coordinates": [
      [
        [0.30, 0.20],
        [0.44, 0.20],
        [0.44, 0.35],
        [0.30, 0.35],
        [0.30, 0.20]
      ]
    ]
  },
  "display_order": 1
}
```

Normalized coordinates ensure the layout works across desktop, tablet and mobile screen sizes.

For complex plot shapes, support multiple polygon vertices and optional multipolygon geometry.

## 4. Detailed inventory and booking workflow

### 4.1 Plot status state machine

mermaid

```mermaid

stateDiagram-v2
    [*] --> Available
    Available --> Hold: Authorized hold
    Hold --> Available: Expired or released
    Hold --> BookingPending: Booking submitted
    BookingPending --> Booked: Manager approves
    BookingPending --> Available: Manager rejects
    Booked --> Registered: Registration completed
    Booked --> Available: Approved cancellation
    Available --> Blocked: Admin blocks
    Blocked --> Available: Admin releases
```

A booking request must never automatically make a plot Booked.

The booking is confirmed only after manager approval and the required business checks.

### 4.2 Booking workflow

| Step | User | Action | Result |
| --- | --- | --- | --- |
| 1 | Salesperson/Broker | Selects available plot | Plot details shown |
| 2 | Salesperson/Broker | Requests temporary hold | Hold request processed |
| 3 | Salesperson/Broker | Adds customer details | Customer linked |
| 4 | Salesperson/Broker | Submits booking | Booking Pending |
| 5 | Manager | Reviews booking | Approve or reject |
| 6 | Manager | Approves booking | Plot becomes Booked |
| 7 | Accounts | Records payment | Payment history updated |
| 8 | Manager/Admin | Completes registration workflow | Plot becomes Registered/Sold |

### 4.3 Booking approval rules

The manager approval screen should display:

- Booking ID.
- Project.
- Plot number.
- Plot area.
- Selling price.
- Customer information.
- Salesperson or broker.
- Booking amount.
- Payment evidence.
- Booking documents.
- Previous plot status.
- Booking remarks.

Available actions:

- Approve.
- Reject.
- Request correction.
- Cancel, where authorized.

Every action requires an audit entry.

### 4.4 Preventing double booking

This is a mandatory backend requirement.

When two users submit a request for the same plot:

1. Backend checks current plot status.
2. Backend validates active hold ownership and expiry.
3. Backend executes a database transaction.
4. Backend locks the plot record or uses an equivalent concurrency-safe conditional update.
5. Only one request succeeds.
6. The second request receives an HTTP 409 Conflict response.

Use PostgreSQL transactions and conditional state transitions. Redis locks alone must never be relied upon as the booking correctness mechanism.

### 4.5 Hold policy

Recommended configurable default:

- Hold duration: 30 minutes.
- Extension: manager-authorized.
- Automatic expiry: enabled.
- Hold release: salesperson or manager according to permission.
- Expired holds: automatically return to Available if no active booking exists.

These values should be configurable by project.

A submitted booking should have a separate pending-review expiry policy. A pending approval must not remain open indefinitely.

### 5.3 Broker-specific rules

Brokers should have a separate account type and organization association.

Each broker can:

- View assigned projects.
- View public and broker-authorized inventory.
- Submit customer leads.
- Request holds.
- Submit booking requests.
- Track their own leads.
- Track their booking commissions.

Brokers must not:

- View other brokers' leads.
- Access internal employee reports.
- Access other brokers' commission records.
- Modify pricing.
- Approve bookings.
- View unrelated customer documents.

A customer lead should have an ownership and attribution record. Duplicate leads must be detected before assigning commission credit.

### 6.3 Additional database requirements

- Use UUID primary keys.
- Use foreign keys on all relational references.
- Use indexes on project\_id, plot\_id, booking\_status, customer mobile and lead assignment.
- Use soft deletion only for records where deletion is appropriate.
- Never physically delete confirmed booking or payment history.
- Maintain created\_at and updated\_at timestamps.
- Use database migrations for schema changes.
- Use decimal/numeric types for all financial values.
- Store timestamps in UTC and render them in the user's local timezone.
- Use database constraints to prevent multiple active bookings for the same plot.

### 6.4 Critical booking database constraint

A partial unique index is recommended:

sql

```sql
CREATE UNIQUE INDEX
  unique_active_booking_per_plot
ON bookings (plot_id)
WHERE booking_status IN (
  'PENDING_APPROVAL',
  'APPROVED'
);
```

The application must also enforce the corresponding plot status transition inside a transaction.

A cancelled or rejected booking must not block future bookings.

## 8. Existing website API integration specification

This integration is a high-priority requirement.

The existing website should continue operating as it currently does, but project and plot information will be fetched from the CRM backend.

### 8.1 Website integration architecture

There are two types of communication:

Website → CRM

- Fetch projects.
- Fetch plot information.
- Fetch current availability.
- Submit customer enquiries.
- Submit booking requests.

CRM → Website

- Notify when a plot becomes unavailable.
- Notify when a hold expires.
- Notify when a booking is rejected or cancelled.
- Notify when plot details change.
- Notify when a project layout is updated.

```json
  }
```


HTTP status: `409 Conflict`.

### 8.7 Webhook reliability

The CRM must implement:

- HMAC-SHA256 webhook signatures.
- Unique event IDs.
- Delivery attempt history.
- Automatic retries with exponential backoff.
- Idempotent event processing.
- Failed-delivery dashboard.
- Manual retry.
- Event timestamp and inventory version.

The website should not rely solely on webhook notifications for its inventory database. It must be able to retrieve the latest inventory snapshot from the CRM after a disconnection.

Important integration rule: Public API reads can be cached briefly, but the final availability check and every booking operation must use authoritative live database state.

## 9. API error handling and security standards

### 9.1 Standard HTTP status codes

| Code | Meaning |
| --- | --- |
| 200 | Successful request |
| 201 | Record created |
| 204 | Successful request without response body |
| 400 | Invalid input |
| 401 | Unauthorized |
| 403 | Permission denied |
| 404 | Record not found |
| 409 | Inventory conflict or duplicate |
| 422 | Business rule validation failure |
| 429 | Too many requests |
| 500 | Internal server error |
| 503 | Service temporarily unavailable |

### 9.2 Security requirements

1. Hash passwords using Argon2id or an appropriately configured secure password hashing algorithm.
2. Use short-lived access tokens and rotating refresh tokens.
3. Enforce project-level and record-level access permissions.
4. Protect public enquiry endpoints from spam and abuse.
5. Use HTTPS for all communication.
6. Validate uploaded files and restrict allowed file types.
7. Encrypt sensitive documents at rest.
8. Keep website API credentials separate from employee accounts.
9. Never expose internal database IDs as authorization credentials.
10. Maintain login and sensitive-operation audit logs.
11. Apply rate limits to public APIs.
12. Implement backup and recovery procedures.
13. Protect against SQL injection, XSS, CSRF and insecure direct object references.
14. Do not expose internal customer records through public APIs.
15. Apply configurable retention policies for personal data.

For Indian operations, the implementation should also account for applicable DPDP Act requirements, consent handling, privacy notices, and applicable real estate regulatory requirements.

### 9.3 Important booking security rule

Only a user with the `booking.approve` permission and access to the relevant project can approve a booking.

The backend must validate the approval permission and the booking state at the moment of approval, not just when the booking screen was first opened.

Mandatory business-critical tests| Test | Expected result |

## 19. Final product definition

# Real Estate CRM & Plot Management System

Finalized product vision

The platform will allow the company to manage all residential plots, projects, employees, brokers, customers, enquiries and bookings through one centralized application.

The five essential capabilities:

1. Interactive project layout with individually editable plots.
2. Real-time plot availability across the CRM and existing website.
3. Role-based access for management, sales employees and brokers.
4. Manager-controlled booking approval with double-booking protection.
5. Centralized customer, lead, payment and sales management.

Technology foundation

- Next.js + React
- NestJS + Node.js
- PostgreSQL + Prisma
- Redis + Socket.IO
- REST APIs + signed webhooks
- AWS-compatible document storage

## My recommendation for the next development step

Start with a clickable CRM prototype and the interactive Ratanpur plot layout before building all the backend modules.

This will validate the most distinctive part of the product: whether the actual numbered plots, their boundaries, their areas and their availability can be represented accurately and managed comfortably by your sales team.

The first development milestone should therefore be:

Milestone 1: Admin login → Create Ratanpur project → Upload layout → Digitize plots → Enter inventory → Click a plot → Change availability → See the updated status.

Once that works, the booking engine and website API can be built on top of the same inventory foundation.
